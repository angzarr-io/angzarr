# Code Review: bus / transport / discovery subsystem

## PRIORITY: AMQP interleave publish-drop (HandleEvent + HandleCommand)

**Status: STILL OPEN — no fix has landed.** No commit since the 2026-04-07 discovery touches this path (`git log` since 2026-04-01 shows only DLQ/storage/registry work), and no test pins the scenario. After tracing the full persist→publish chain, the bus-side `AmqpEventBus::publish` itself is sound (publisher confirms enabled per channel, nack/NotRequested handled, 5x retry with backoff). The drop has to occur in the persist/publish orchestration above it, and there is exactly one live mechanism that deterministically produces "persisted at correct sequence, never published":

**HIGH | src/orchestration/aggregate/pipeline.rs:376-388 (`publish_unless_noop`) + src/orchestration/aggregate/grpc/mod.rs:453-477 (`persist_events` NoOp classification) | Retry-after-persist re-execution classifies as NoOp and permanently skips publish.**
Sequence: (1) command attempt persists events at seq N but `post_persist` publish fails → mapped to `Status::unavailable` (grpc/mod.rs:596), which `is_retryable_status` (src/utils/retry.rs:169) treats as retryable; (2) `execute_command_with_retry` re-runs the whole pipeline; (3) prior events now *include* seq N, business logic re-invoked against updated state returns no new diff; (4) `persist_events` returns `PersistOutcome::NoOp` (`new_pages.is_empty() && !snapshot_changed`, grpc/mod.rs:475); (5) `publish_unless_noop` skips publish (H-16) and the pipeline returns **success**. The event is in the store and never on the bus. The v0.4.1 "republish on redelivery" fix (`try_deferred_idempotency_replay`, pipeline.rs:155-190) only covers commands carrying an `AngzarrDeferred` header **with full source provenance** — `extract_source_info` (pipeline.rs:125-144) returns `None` when `source.domain`/`root` are absent, and the fact pipeline explicitly persists with `source_info: None` (pipeline.rs:845). The HandleEvent interleave is what manufactures the retry (the fact steals seq 2, the command's first attempt hits `FAILED_PRECONDITION` / publish races) and what makes the re-executed handler see already-applied state. The H-16 fix created this gap: "NoOp must not reach the bus" conflated "nothing persisted" with "persisted previously but unpublished."
*Fix direction:* on retry, when persist returns NoOp but the prior load shows events at the sequence the command would have produced, republish those events (extend the replay path to fact/external_id provenance, or track "persisted-but-unpublished" explicitly — an outbox marker would close this class entirely).

Two secondary mechanisms consistent with the symptom, both still present:

**HIGH | src/bus/amqp/mod.rs:737-754 | Unroutable AMQP publishes are confirmed as success.** `basic_publish` is called without the `mandatory` flag; RabbitMQ basic.acks a confirmed message even when it routes to **zero queues**. If the subscriber's queue/binding isn't established (consumer restart window, first deploy), publish() returns Ok and the message is silently dropped — broker confirm ≠ delivery. *Fix:* set `mandatory: true` and treat returned messages (`Confirmation::Ack(Some(_))`/return callback) as publish failure.

**HIGH | src/handlers/core/saga.rs:74,113,168-176 | Sagas are at-most-once by default.** `propagate_errors: false` (and `with_error_propagation(true)` is never called anywhere in production code), so any `orchestrate_saga` failure is logged and the source event is **acked**. PM and aggregate handlers default to `true` (process_manager.rs:78). A transient saga failure on the DecisionPending event would also present as "saga never received it." *Fix:* flip the saga default to propagate (loud-fail) to match PM/aggregate, or wire the saga DLQ at this site.

## Remaining findings (by severity)

**CRITICAL | src/bus/kafka/bus.rs:203-221 | Kafka consumer silently loses failed messages (at-most-once behind an at-least-once trait).** On handler failure the offset is "not committed," but the loop continues to the next message; the next successful `commit_message` commits a **higher** offset, which implicitly commits past the failed one. The failed message is never redelivered — directly contradicting AMQP's nack/requeue semantics behind the same `EventBus` trait, and the comment at amqp/mod.rs:614-616 that claims they match. *Fix:* on failure, stop/seek the partition back to the failed offset (or pause + retry in place, or route to a retry/DLQ topic) instead of continuing.

**HIGH | src/bus/pubsub/bus.rs:166-171, src/bus/sns_sqs/bus.rs:405-410 | `subscriber_all` receives nothing on Pub/Sub and SNS/SQS.** With empty `domains`, both consume from the literal pseudo-domain `"events"` (topic `{prefix}-events-events`), while publishers write to per-domain topics. The "subscribe-side filtering will be used" warning is dead code — no messages ever arrive to filter. AMQP (`#` binding) and Kafka (regex `^prefix\.events\..*`) handle all-domains correctly. `create_subscriber(name, None)` is therefore broken on these two backends. *Fix:* enumerate/list topics (or use a single fan-in topic) for the all-domains mode.

**HIGH | src/bin/angzarr_aggregate.rs:156-170 + src/bus/config.rs:48 | Misconfigured messaging silently degrades to MockEventBus / default config cannot boot.** The aggregate bin matches only `messaging_type == "amqp"`; configuring `kafka`/`pubsub`/`sns-sqs` (all real backends in the factory) falls into the `_ =>` arm: events persist but are **never published** — the exact symptom class of the open bug, as a config trap. It also bypasses `init_event_bus`, `InstrumentedBus`, and `wrap_with_offloading`. Separately, `MessagingConfig::default()` is `"channel"` but the channel backend was removed (commit b1eb2416) — no `inventory` registration matches, so `init_event_bus` returns `UnknownType` for default config while doc comments still advertise "channel". *Fix:* route the bin through the factory and hard-fail on unknown/unsupported messaging types; update the default.

**HIGH | src/bus/amqp/mod.rs:655-666, src/bus/sns_sqs/consumer.rs:214-223, src/bus/pubsub/consumer.rs:87-92 | Handler-failure paths never reach DLQ; unbounded poison loops.** AMQP nacks with `requeue: true` with no delivery-count cap — a deterministic handler failure redelivers forever and the H-06 DLX only fires for decode-rejects/TTL/max-length, never for handler failures. SQS queues are created with no redrive policy (`maxReceiveCount`), so a poison message cycles on visibility timeout forever **and, being FIFO, permanently blocks its message group** (all subsequent events for that aggregate root). Pub/Sub subscriptions are created without a `dead_letter_policy`. *Fix:* cap redeliveries (`x-delivery-count` via quorum queues or header counting) and reject-to-DLX on exhaustion; set SQS redrive policy and Pub/Sub dead-letter policy at creation.

**MEDIUM | src/bus/amqp/mod.rs:587-595 | No `basic_qos` on the AMQP consumer — unbounded prefetch.** Without a prefetch limit RabbitMQ pushes the entire queue backlog to one consumer: unbounded memory on slow consumers, no load distribution across replicas, and nack-requeued messages re-enter behind a huge in-flight window (worsening reordering). *Fix:* `basic_qos(prefetch_count)` before `basic_consume`.

**MEDIUM | src/bus/pubsub/bus.rs:199-235, src/bus/sns_sqs/consumer.rs:214-223 | Batch processing continues after a failure, breaking per-root ordering.** Both consumers pull a batch, and when message N fails (nack / left to visibility timeout) they continue processing N+1 — which may share the same ordering key / FIFO group. N is then redelivered *after* N+1 was handled. The framework pays for ordered delivery (`enable_message_ordering`, FIFO topics) and then voids it consumer-side. *Fix:* on failure, stop processing the remainder of the batch for that ordering key (or entirely) before re-polling.

**MEDIUM | src/discovery/k8s/mod.rs:592-597, 710-728 | Service deletions never propagate to the inner registry; stale clients served forever.** `Event::Delete` removes from the watcher cache only; `StaticServiceDiscovery`'s service map and cached gRPC clients are never invalidated, and `get_aggregate`/`get_all_projectors` re-register every cached service into inner **on every lookup** (O(n) write-lock churn per call). A deleted/moved aggregate keeps resolving to the dead endpoint. *Fix:* propagate deletes to inner (add `unregister_*`) and drop the per-call re-sync in favor of event-driven sync.

**MEDIUM | src/bus/kafka/bus.rs:163-237 | Kafka consumer task dies silently; no reconnect loop.** The spawned task exits if the stream ends, and consumer errors (line 232) are only logged with no backoff/health signal — in contrast to AMQP's `consume_with_reconnect` and the K8s watchers' H-07-fixed loops. Also, calling `start_consuming` twice spawns two competing stream loops over the same `StreamConsumer`. *Fix:* wrap in a reconnect loop with backoff + liveness signal; guard against double-start.

**MEDIUM | src/bus/offloading.rs:94-107 | Offloading can pass through oversized books.** A book whose total size exceeds the threshold but whose individual pages are each ≤ threshold/2 offloads nothing (per-page gate `page_size > threshold / 2`), and there is no post-offload re-check of total size — the inner bus/broker then rejects (SNS 256 KiB is easy to hit with many small pages). *Fix:* after the page pass, re-check `encoded_len()` and offload further pages (largest-first) until under threshold, or error explicitly.

**MEDIUM | src/bus/amqp/mod.rs:225-237 | Channel-per-publish is never closed; confirm_select round-trip per publish.** Every publish creates a fresh channel on a pooled connection and drops it without `close()`. If lapin (v2) doesn't close on drop in this configuration, channel IDs accumulate toward RabbitMQ's per-connection cap (2047) and publishes start failing after sustained traffic; even if drop closes, the create-channel + confirm_select handshake adds 2 RTTs per publish. *Fix:* verify lapin drop semantics; pool confirmed channels (deadpool object = channel) instead of connections.

**MEDIUM | src/discovery/k8s/mod.rs:99,221-231 | 30s watcher-health threshold will report unhealthy in any quiet cluster.** Watcher streams only yield items on change or re-list (~5 min apiserver watch timeout); in a cluster with no Service churn, `is_watcher_healthy` is false most of the time. If wired to the documented helm liveness probe, that's a restart loop. *Fix:* raise the threshold above the watch re-list interval, or record stream-level keepalives (bookmarks) rather than only events.

**LOW | src/orchestration/aggregate/grpc/mod.rs:102-106 vs src/proto_ext/books.rs:33-39 | Two same-named `calculate_set_next_seq` helpers disagree on empty books** (grpc-local yields `1`, proto_ext yields `0`). The grpc-local one feeds `build_event_book` for idempotency-replay books — latent today (replay books always have pages) but a drift trap. *Fix:* delete the local copy, use the proto_ext one.

**LOW | src/orchestration/command/grpc/mod.rs:30-31,65 | `Mutex<Client>` held across the gRPC await serializes all command execution per domain.** tonic clients are `Clone` (cheap channel handle); the lock is unnecessary and creates head-of-line blocking for every saga/PM targeting one domain. Also doc drift at src/orchestration/command/mod.rs:43: claims CASCADE does "no bus publishing," but `post_persist` (grpc/mod.rs:589-596) publishes in all non-ISOLATED modes.

**LOW | src/bus/traits.rs:44-56 + src/handlers/core/aggregate.rs:219 | `CommandBus` has zero implementations and `wrap_command_for_bus` zero callers** — the saga handler's async command-bus branch (saga.rs:255-268) can never execute. Per project convention: flag for a **wire-or-delete decision** (this is the documented "async fire-and-forget command" contract), not dead code.

**LOW | src/bus/pubsub/bus.rs:77-87 | TOCTOU on topic exists/create** — two concurrent first publishes to a new domain race; the loser gets `AlreadyExists` and the publish fails (SNS/SQS `create_*` are idempotent, Pub/Sub `create` is not). *Fix:* treat AlreadyExists as success.

## Overall assessment

The AMQP backend is the most hardened (confirms, DLX, backoff discipline with named fix IDs), but the same `EventBus` trait hides materially different delivery semantics: Kafka can silently lose failed messages, Pub/Sub and SNS/SQS have a broken all-domains mode and no handler-failure DLQ path, and the saga handler is at-most-once by default — so the framework's at-least-once story currently holds only for AMQP with well-behaved handlers. The open interleave bug is best explained by the NoOp-on-retry publish skip (H-16's blind spot) compounded by AMQP's unroutable-publish-equals-success behavior; closing those two plus an outbox-style "persisted-but-unpublished" marker would eliminate the entire "persisted but never published" class. Transport and discovery are largely sound apart from stale-endpoint retention after K8s deletes and the over-aggressive watcher health threshold.
