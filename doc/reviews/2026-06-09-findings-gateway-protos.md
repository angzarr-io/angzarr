## Findings Report

**CRITICAL | gateway/main.go:22 | Gateway is built against a stale, pre-v1 proto package — fresh builds break, stale builds get UNIMPLEMENTED**
The protos in the submodule now live at `angzarr_client/proto/angzarr/v1/*.proto` with package `angzarr_client.proto.angzarr.v1`, and the Rust coordinator serves that package (`src/proto.rs:8: tonic::include_proto!("angzarr_client.proto.angzarr.v1")`). But `main.go` imports `gw "github.com/angzarr-io/angzarr/gateway/gen/angzarr_client/proto/angzarr"` (no `/v1`), and the gitignored local `gen/` tree matches that old layout — its generated method names are `/angzarr_client.proto.angzarr.EventQueryService/Synchronize` (no `.v1`, see `gen/.../query.pb.gw.go:317`). Since the Containerfile regenerates with `buf generate` (`paths=source_relative` → output lands in `gen/angzarr_client/proto/angzarr/v1/`), the container build of main.go fails to compile; conversely a binary built from the stale gen would get UNIMPLEMENTED from the v1 Rust server on every coordinator route. Fix: regenerate, update imports to the `/v1` paths, and add a CI build of the gateway image so proto-package migrations can't silently strand it.

**HIGH | angzarr-project/proto/.../v1/types.proto:31,190,221-222,258-260,309,370 | Removed field numbers are not `reserved` — wire-compat reuse hazard**
Multiple messages document removed fields with comments only: `Cover` ("Field 5 removed: external_id"), `EventPage` (field 5), `EventBook` (fields 4, 5), `CommandBook` (fields 3, 4, 5), `Query` (field 2), `RejectionNotification` ("Fields 3-6 removed"), and `Snapshot` silently skips field 1. None carry `reserved` declarations, while `Notification` (line 355-356), `CommandResponse` (command_handler.proto:86-87) and `SagaCompensationFailed` (saga.proto:66-67) do — so the convention exists but is applied inconsistently. A future field added at one of these numbers will silently misparse old persisted events (fatal in an event-sourcing store that replays history forever). Fix: add `reserved N; reserved "name";` for every removed field across types.proto.

**HIGH | angzarr-project/proto/.../v1/types.proto:233-236 | `EventRequest.route_to_handler` documents "default: true" but proto3 bool default is false**
The comment says "when true (default), invokes command handler's handle_fact… When false, facts are persisted directly without handler involvement," and command_handler.proto:125 repeats "(default: true)". A proto3 `bool` cannot default to true — a client that omits the field gets handler-bypass persistence, the exact opposite of the documented contract, and fact validation silently never runs. Fix: invert to `bool skip_handler` (false = route to handler, matching the documented default), or make it an enum with `_UNSPECIFIED = 0` mapped server-side to "route".

**HIGH | gateway/main.go:143-146 | No HTTP server timeouts and no upstream deadline on any request path**
`server := &http.Server{Addr: addr, Handler: mux}` sets no `ReadHeaderTimeout`/`ReadTimeout`/`IdleTimeout` (Slowloris and idle-connection exhaustion), and the gateway never sets `runtime.DefaultContextTimeout` or a deadline-injecting middleware, so a hung coordinator call pins the HTTP connection and goroutine indefinitely — this is the only ingress for the whole framework. Fix: set `ReadHeaderTimeout`/`IdleTimeout` on the server, and apply a per-request `context.WithTimeout` for unary routes (exempting the streaming paths `/v1/stream/`, `/v1/query/.../events/stream`, which legitimately need long lifetimes and therefore no `WriteTimeout`).

**MEDIUM | gateway/main.go:140 | Unbounded request bodies on all POST routes**
grpc-gateway unmarshals the entire JSON body into a proto message in memory; nothing wraps the handler in `http.MaxBytesReader`, so `POST /v1/ch/{domain}/commands` (body: `*`, contains arbitrary `Any` payloads) accepts arbitrarily large bodies — trivial memory-exhaustion DoS, and oversized payloads only fail later at the gRPC 4MB frame limit with a confusing 500. Fix: a small middleware applying `http.MaxBytesReader(w, r.Body, limit)` before `gwMux`.

**MEDIUM | gateway/buf.gen.yaml:26 | `generate_unbound_methods=true` exposes RPCs the protos explicitly exclude from REST**
query.proto:25 says "Bidirectional sync - not exposed via REST (use gRPC directly)", but the gateway plugin runs with `generate_unbound_methods=true` and main.go registers the full `EventQueryService` handler, so `POST /angzarr_client.proto.angzarr.v1.EventQueryService/Synchronize` becomes a live route (visible in the generated `query.pb.gw.go:226`). Bidi streaming over the gateway's HTTP/1.1 transcoding is half-duplex at best and will misbehave. Fix: drop `generate_unbound_methods` (everything intentionally public already has `google.api.http` annotations).

**MEDIUM | angzarr-project/proto/.../v1/types.proto:80-86,102-107 | Behavior-bearing enums use meaningful zero values instead of UNSPECIFIED**
`SYNC_MODE_ASYNC = 0`, `MERGE_COMMUTATIVE = 0`, `CASCADE_ERROR_FAIL_FAST = 0`, while newer enums in the same file/repo (`PAYLOAD_STORAGE_TYPE_UNSPECIFIED = 0`, `REJECTION_TYPE_UNSPECIFIED = 0`, `REPLAY_MODE_UNSPECIFIED = 0`) follow the convention. The worst is SyncMode: a REST client that simply omits `sync_mode` on `POST /v1/ch/{domain}/commands` silently gets fire-and-forget — no accept/reject visibility — indistinguishable from an intentional ASYNC request, and the server can never tell "unset" from "asked for async". Renumbering now is a breaking change, but adding `*_UNSPECIFIED` aliases is not possible at 0; at minimum document the deliberate defaults and apply the UNSPECIFIED convention to all future enums (and decide before the API freezes whether SyncMode is worth a one-time renumber).

**MEDIUM | gateway/discovery/schema.go:117 + openapi.go:53-54,107 | Patched OpenAPI spec emits dangling $refs and OpenAPI-3 keywords in a Swagger 2.0 document**
`PatchOpenAPISpec` registers discovered schemas under `"discovered." + name`, but message-typed fields generate `Ref: "#/definitions/" + shortName` (no prefix) — every nested-message reference in `/openapi.json` is dangling. Additionally `buildOneOfDefinition` emits `oneOf` into a `"swagger": "2.0"` document (confirmed in `api/angzarr.swagger.json`), which is invalid in OpenAPI v2 and breaks strict tooling. Collision fallback in `GenerateSchemas` (full name with underscores) makes refs to collided types point at the wrong schema too. Fix: generate refs with the same `discovered.` prefix/keying as the definitions map, and use `x-oneOf` or upgrade the spec to OpenAPI 3.

**MEDIUM | gateway/Containerfile:28 | `go mod tidy` at image build time — non-hermetic, go.sum effectively ignored**
The repo has a committed `go.sum`, but the build runs `RUN go mod tidy` after generation, re-resolving dependency graph and rewriting go.sum inside the container, so builds are not reproducible and the committed checksums provide no supply-chain pinning. The comment on line 8 ("buf v1.47.2 works with Go 1.23") has also drifted from the `golang:1.24-alpine` base. Fix: commit the generated-code import set's deps in go.mod, use `go mod download` + `go build -mod=readonly`, and pin via the committed go.sum. (Credit where due: the runtime stage is `distroless/static:nonroot` — non-root, no shell, no build cache copied — that part is right. No container HEALTHCHECK, but on k8s probes are the right mechanism; see next finding for why the probe target is weak.)

**MEDIUM | gateway/main.go:54,110-113 | `/health` always returns ok and the lazy gRPC client never surfaces a bad GRPC_TARGET**
`grpc.NewClient` does not dial (connection is lazy), so a typo'd `GRPC_TARGET` passes startup, and `/health` unconditionally writes 200 "ok" without consulting `conn.GetState()` or the upstream's `grpc.health.v1.Health` service (which exists — proto/health/v1/health.proto). Kubernetes readiness wired to `/health` will route traffic to a gateway that can reach nothing. Fix: have `/health` check `conn.GetState()` or proxy a deadline-bounded `Health.Check` to the coordinator.

**LOW | gateway/main.go:54 | Transport hardcoded to insecure with no TLS escape hatch**
`grpc.WithTransportCredentials(insecure.NewCredentials())` is fine for the intended same-pod sidecar at `localhost:1310`, but `GRPC_TARGET` is freely configurable to any address, in which case command traffic (including correlation IDs and payloads) crosses the network in plaintext with no option to do otherwise. Fix: add a TLS config flag/env (CA bundle + optional mTLS), defaulting to insecure only for loopback targets.

**LOW | query.proto:21-27, stream.proto:18-20 | Protos promise "SSE" but grpc-gateway emits newline-delimited JSON**
Comments on `GetEvents`, `GetAggregateRoots`, and `Subscribe` say "REST: Server-Sent Events (SSE) stream", but the default gateway forwarder streams chunked `{"result": ...}` NDJSON with `Content-Type: application/json` — a browser `EventSource` against `/v1/stream/{correlation_id}` will fail. Fix the comments, or add a real SSE `runtime.Marshaler`/forward-response writer for those routes.

**LOW | gateway/main.go:61 | Default ServeMux: no incoming header matcher, no CORS**
`runtime.NewServeMux()` with no options means only `Grpc-Metadata-*` and permanent headers are forwarded to the coordinator — `traceparent`/`X-Correlation-ID` style headers are dropped. This is survivable only because the framework carries correlation in-body (`Cover.correlation_id`); but nothing at the gateway validates that required field is set on initial commands, and combined with the ASYNC-default SyncMode a missing correlation fails silently downstream. There is also no CORS middleware, so the angzarr-status SPA can only consume `/api/dlq` same-origin. Fix: add `runtime.WithIncomingHeaderMatcher` for tracing headers, a CORS layer (configurable origins), and consider gateway-side rejection of command POSTs with empty `command.cover.correlation_id`.

**LOW | proto/angzarr/status/dlq_admin.proto:17,107-116,126-128 | DLQ admin surface inconsistencies and self-contradictory NOT_FOUND contract**
Package `angzarr_client.proto.angzarr.status` lacks a version segment (every sibling is `.v1`) and its REST prefix is `/api/*` while all other routes are `/v1/*`. The `Health<T>` envelope means backend failure returns HTTP 200 + `degraded` (RFC 7807 *body* without 7807 status-code semantics — monitors keying on status codes see all-green). And `GetDeadLetterOk`'s comment contradicts itself: "an ok response with entry unset means no row matches (gRPC NOT_FOUND is the wire-level signal)" — it can't be both an OK envelope and a NOT_FOUND status. Pick one (the envelope, given the tile design) and fix the comment; version the package before the SPA hardens against it.

**LOW | gateway/discovery/service.go:19 vs descriptor.go:73 | Doc says `DISCOVERY_DESCRIPTOR_FILE`, code reads `DESCRIPTOR_PATH`**
`NewService`'s doc comment names an env var that does not exist; the actual constant is `DescriptorPathEnvVar = "DESCRIPTOR_PATH"`. An operator following the comment gets the silent "no descriptor file configured" path and an unpatched spec. Related minor duplication: `Service.GetInfo` (service.go:103) reimplements `GetDiscoveryInfo` (openapi.go:120) with a different JSON shape, and Containerfile:37 copies `api/` into the runtime image although main.go embeds it via `go:embed`.

---

**Overall assessment:** The proto layer is thoughtfully designed (good removal comments, deliberate 2PC/claim-check modeling, the Target unification done) but its compat hygiene is inconsistent — the unreserved removed fields and the false `route_to_handler` default are real wire-contract bugs in an event store that replays forever. The gateway Go code is clean but minimal to a fault: no timeouts, no body limits, no health truth, and — most urgently — it is pinned to a pre-`v1` proto package, so as written it either fails to build in its own Containerfile or speaks method names the v1 Rust coordinator no longer serves. Priority order: fix the v1 package drift (and add a gateway build to CI), reserve the removed field numbers, fix `route_to_handler`, then harden the HTTP server.
