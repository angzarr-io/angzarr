## Findings Report

**HIGH | src/utils/response_builder/mod.rs:37-50 | Business `Notification` responses are silently swallowed in the command pipeline**
`extract_events_from_response` consumes `BusinessResponse` by value; the `Result::Notification(notification)` arm logs at `debug!` and returns an empty `EventBook`, with a comment "notification forwarding handled separately". A repo-wide grep shows `business_response::Result::Notification` is matched **nowhere else** in production code, and the only callers (`pipeline.rs:578,663`) just persist the empty book. A handler that returns a notification to forward a rejection upstream has it dropped on the floor with success semantics. Fix: either return the notification to the caller (e.g. a richer enum like `ExtractedResponse::{Events, Notification}`) and wire forwarding, or reject the variant loudly until forwarding exists.

**HIGH | xtask/src/main.rs:104-133, 181-193 | gen-mutants-exclude regexes are unanchored substrings — can exclude mutants it shouldn't, and silently fail to exclude others**
Generated patterns like `Foo::get` and `<impl .*Trait.* for Type>::method` are matched by cargo-mutants as unanchored regexes, so `Foo::get` also suppresses `Foo::get_balance`, and the `.*` padding around the trait name matches any trait containing that substring on the same self type (e.g. marking `<impl .*Name.* for X>::id` would also hit `<impl ComponentName for X>::id...`). In the opposite direction: `type_to_string` returns `".*"` as an intended wildcard for non-path self types but `add_function` then passes it through `regex_escape`, producing `\.\*` which matches nothing; and free functions emit `::{name}` (main.rs:129) while cargo-mutants names free-fn mutants without a leading `::`, so those exclusions never fire. Fix: anchor patterns (`>::method\b` / `$`-ish boundaries, or match cargo-mutants' exact name format), don't escape intentional wildcards, and verify each generated pattern against `cargo mutants --list` output.

**HIGH | crates/trivial-delegation/src/lib.rs:31-41 | `#[trivial_delegation]` enforces nothing — it can hide arbitrary logic (or whole impl blocks) from mutation testing**
The macro is `parse_macro_input!(item as Item)` + unconditionally prepending `#[mutants::skip]`/`#[coverage(off)]`. It accepts *any* item: a 50-line function with real branching, or even an entire `impl` block / module — `#[mutants::skip]` on an impl block skips every method inside, and xtask's visitor would also record it. Given the project's "tests must kill mutants" pillar, this is a soft spot: one mislabeled attribute silently removes code from the 90%-kill-rate contract. Fix: in the macro, parse as `ItemFn`/`ImplItemFn` only and verify the body is a single expression/statement (optionally allowing one `map_err`), emitting a compile error otherwise. Current usages (4 getters in `process_manager/grpc/mod.rs`) are legitimate.

**MEDIUM | src/proto_ext/books.rs:33-44 + src/orchestration/aggregate/grpc/mod.rs:102-106 | Two divergent `calculate_set_next_seq` implementations; the proto_ext one ignores the snapshot whenever pages exist**
`proto_ext::calculate_next_sequence` returns `last_page.sequence_num() + 1` if any page exists, else `snapshot.seq + 1`, else 0 — so a book whose last page is deferred (`sequence_num()` → 0) or whose snapshot is ahead of its pages yields a wrong, *lower* next_sequence (e.g. snapshot at 10 + deferred tail page → next=1). Meanwhile `aggregate/grpc/mod.rs` defines a private shadow with different semantics: `max(last_page, snapshot) + 1`, which returns 1 (not 0) for an empty book. Two helpers computing the framework's sequencing primitive with divergent edge behavior is exactly the multiply-across-the-codebase hazard; also both are free functions over proto types, against the extension-trait convention. Fix: single `EventBookExt` method with `max(pages, snapshot)` semantics, explicit deferred-page handling, and delete the local duplicate.

**MEDIUM | src/utils/saga_compensation/mod.rs:522-549, 706-712 | Compensation root hash includes volatile failure-reason text, undermining the H-37 idempotency invariant**
`derive_compensation_root_bytes` hashes `compensation_failure_reason`, but the fallback paths synthesize that reason from transient detail: `reason: format!("gRPC error: {}", status)` (line 711). Two redeliveries of the same failed saga command that hit different transient errors (e.g. "connection refused" vs "deadline exceeded") derive *different* roots and land on different fallback-domain aggregates — the exact non-idempotency H-37 was fixed to remove, just one layer up. Fix: exclude the reason from the hash (provenance + command bytes already discriminate the logical failure), or hash a stable reason classifier (enum tag) instead of the formatted string.

**MEDIUM | src/utils/saga_compensation/mod.rs:268-309 | Webhook `notify()` swallows terminal failure — `escalate=true` can silently no-op**
After all retries are exhausted the function logs and `return Ok(())` (line 308), and 4xx client errors also return `Ok(())` (line 276). The `CompensationError::EscalationFailed` variant is therefore unreachable on the webhook path, and `process_revocation_flags`' "log but continue on escalation error" branch never sees the failure — operators relying on the escalate flag get only a log line. Fix: return `Err(EscalationFailed)` on exhaustion/4xx and let the caller's existing error-isolation logging handle it (behavior stays non-fatal, but the failure becomes observable to callers and metrics).

**MEDIUM | src/utils/saga_compensation/mod.rs:147-157, 850 | Per-call `DefaultEscalationHandler` construction with `.expect()` on reqwest client build**
`process_compensation_response` constructs a fresh `DefaultEscalationHandler` (and thus a fresh reqwest `Client` + connection pool) on every compensation response; `Client::builder().build().expect(...)` panics on TLS/backend init failure — a panic path executed *during failure handling*, where the process is least able to afford it. Fix: build the handler once at sidecar startup and pass it in (or `Arc` it on config), converting the build error into a startup-time `Result`.

**MEDIUM | src/proto_ext/pages.rs:253-265 | `idempotency_key()` panics on missing `source` and has zero production references**
`self.source.as_ref().expect("source required")` will panic the process on a malformed/hand-built `AngzarrDeferredSequence` — in a helper whose documented purpose is "logging and display". Grep shows no production callers of `idempotency_key()` (the `idempotency_key` strings in `src/dlq/` are an unrelated field). Per project convention this is a wire-or-delete decision, but if kept, the panic must go (return `Option<String>` or render `"?"` for missing source) — display helpers must not be able to take down a coordinator.

**MEDIUM | src/proto_reflect/mod.rs:370-399 | `diff_fields` has no type-URL equality guard; mismatched types produce garbage diffs feeding merge decisions**
`diff_fields(before, after)` decodes each `Any` against its own descriptor, then `diff_dynamic_messages` iterates only `before.descriptor().fields()` and calls `after.get_field(&field)` with foreign field descriptors — the code's own comment admits "We assume both messages are the same type." The sole production caller (`merge.rs::diff_state_fields:179`) happens to check `before.type_url != after.type_url` first, but `diff_fields` is `pub` and documented as the commutative-merge primitive; any future caller skipping that guard gets a plausible-but-wrong field set, which can wrongly declare two writes disjoint and merge them. Fix: return `Err`/`"*"` inside `diff_fields` when type URLs (or descriptors) differ, making the guard impossible to forget.

**LOW | src/utils/single_sequence_check.rs:53-66 vs src/utils/retry.rs:171-179 | Contradictory retryability docs on a fragile string-prefix contract**
`sequence_mismatch_error` doc says "This is NOT automatically retryable", yet `is_retryable_status` explicitly classifies messages starting `"Sequence mismatch:"` as retryable (the saga/PM path retries them). Retryability hinges on two modules agreeing on exact message prefixes — rewording either format string silently flips behavior from retry to DLQ-immediate. Fix: correct the doc, and prefer a structured marker (status detail or `errmsg`-style shared constants used by both sides) over message-prefix matching.

**LOW | src/advice/instrumented_handlers.rs:188-217 | PM duration metric lacks the `outcome` attribute the saga/projector wrappers emit**
`InstrumentedPMHandler::handle` records `PM_DURATION` with component/name/domain only, while `SAGA_DURATION`/`PROJECTOR_DURATION` carry `outcome_attr`. `ProcessManagerHandleResult` does encode success/failure, so failure latencies are silently folded into success latencies for PMs only, breaking dashboard symmetry across the four handler types. Fix: derive an outcome label from the result variant; also consider instrumenting `handle_revocation` (currently a bare pass-through).

**LOW | src/advice/lossy.rs:226-234, 266-273 | LossyBus subscriber wrapping discards stats observability**
`create_subscriber` wraps the child in `LossyDynBus::wrap(...)` with *fresh* `LossyStats` and returns `Arc<dyn EventBus>` — the concrete `stats()` accessor is unreachable through the trait object, and the parent's `observed_drop_rate()` never reflects subscriber-side drops. For a chaos-testing tool whose point is asserting observed drop rates, the numbers are misleading in any subscriber topology. Fix: share the parent's `Arc<LossyStats>` with wrapped subscribers (it's already an `Arc`).

**LOW | src/utils/response_builder/mod.rs:80-115 | `publish_and_build_response`/`build_command_response` are unreferenced and bypass the H-16 NoOp guard**
Zero production references (pipeline uses `publish_unless_noop` instead). Per convention: wire-or-delete decision, not dead code — but note that if wired as-is, this helper publishes unconditionally, so a NoOp book would reach the bus, regressing the H-16 fix the pipeline carefully enforces.

**LOW | xtask/src/main.rs:55-58, 210-242 | Empty-scan early return leaves stale exclusions; rewrite assumes CWD = repo root**
If the last `#[trivial_delegation]` is removed, `gen_mutants_exclude` prints "No attributes found" and returns *without* clearing `exclude_re`, leaving stale patterns that suppress now-real mutants. The relative globs and `.cargo/mutants.toml` path also depend on invocation from the workspace root — run from a subdirectory, a partial scan would overwrite the array with a subset. Fix: always rewrite the array (empty if none found) and resolve paths from `CARGO_MANIFEST_DIR`/workspace root.

---

**Overall assessment.** The advice layer is in good shape — metrics are recorded after outcomes are known, no locks held across awaits, and the advice/status metrics namespace separation is clean (status/metrics.rs mentions the `angzarr.*` namespace only in a doc comment). The real risk concentration is in the mutation-testing toolchain (findings 2 and 3 compound: an unenforced macro feeding an imprecise regex generator means the 90%-kill-rate contract is softer than it appears) and in the saga-compensation path, where the swallowed Notification, volatile-reason hashing, and silenced webhook failures all degrade exactly the failure-handling guarantees that subsystem exists to provide. proto_ext/proto_reflect are largely sound, with the sequencing-helper divergence (finding 4) being the one item I'd fix before it propagates further.
